# Playbook 00：漏洞评估与渗透报告方法论（四阶段）

> 覆盖：全流程｜源域 vulnerability-assessment + pentest-reporting
> 定位：贯穿所有 playbook 的通用方法论——先读本 playbook，再进具体漏洞 playbook。

## 1. 目标识别与确认（先过 Scope Guard）

- 明确本次测试的授权范围：目标 / 授权类型 / 授权来源 / 有效期 / 边界（哪些功能与数据不可触碰）。
- `scope init` + `scope add` 写入 scope.json；每个新目标先 `scope check` 确认放行。
- SRC / 真实目标：先读取平台授权范围与测试规则（scope 页面 / 授权邮件），确认目标 in-scope 后再登记授权。
- 记录授权依据（授权邮件 / 平台范围页 / 合同条款类），供报告引用。

## 2. 四阶段方法论

### 阶段一：侦察（Reconnaissance）→ 产出「资产清单」

- 活动：只读收集应用入口、技术栈（框架 / 语言 / 中间件）、功能清单、输入面、认证方式。
- 方法：访问应用、查看页面源码与响应头、阅读公开文档、使用浏览器开发者工具观察请求；不做扫描器批量探测。
- SRC 场景：只列平台授权范围内的资产，不在范围外的资产一律不碰。
- 出口标准：资产清单列出每个入口的 URL / 功能 / 技术特征 / 潜在输入点。

### 阶段二：发现（Discovery）→ 产出「测试点清单」

- 活动：对照 playbook 把资产清单映射到测试点：每个输入点对应哪些漏洞假设。
- 方法：输入点枚举（查询参数 / 表单 / JSON / XML / Cookie / Header / 上传下载）、角色与权限清单。
- 出口标准：测试点清单含优先级（先验证影响面大的），每项标注对应 playbook。

### 阶段三：验证（Verification）→ 产出「验证记录」

- 活动：对候选假设做最小化验证，用「类」表述构造验证输入，观察行为差异。
- 方法：对照每个 playbook 的判定标准；先做只读验证，确认可复现差异即记录证据。
- SRC 场景：验证到「可复现差异」即止，不深挖未授权数据；真实用户数据最小化接触。
- 出口标准：验证记录含请求 / 响应证据、可复现步骤、影响评估；误报被排除并记录原因。

### 阶段四：报告（Reporting）→ 产出「报告草稿」

- 活动：按 references/report-template.md 汇总发现，按严重级排序，给出修复建议。
- 方法：`report generate findings.json --out report.md` 成稿；确认敏感凭据已脱敏。
- SRC 场景：按平台模板整理提交稿（标题 / 影响 / 复现步骤 / 危害等级 / 修复建议）。
- 出口标准：报告含目标 / 时间 / 发现 / 证据 / 修复建议；每轮操作留痕可查。

## 3. 漏洞评估（Vulnerability Assessment）

- 严重级判定（critical / high / medium / low / info）：结合技术影响（数据泄露 / 提权 / 远程执行类）+ 业务影响（资产价值 / 暴露面）+ 可利用性（是否需要前置条件）。
- 证据质量：可复现（同一输入两次结果一致）优于单次观察；记录环境与版本。
- 误报排除：区分「行为差异」与「真实漏洞」；用对照实验（正常输入 vs 异常输入）确认。
- SRC 场景：危害定级参考平台漏洞定级标准（如 CVSS / 平台自定），并说明影响面与触发条件。
- 影响描述用「类」表述：说明可能造成的后果，不写利用链细节。

## 4. 渗透报告方法论（Pentest Report）

- 报告结构（模板见 references/report-template.md）：
  1. 目标与授权信息（授权类型 / 授权来源 / 有效期 / 范围边界）
  2. 摘要（按严重级统计发现数量）
  3. 发现明细（标题 / 严重级 / 类别 / CWE / 端点 / 描述 / 证据 / 修复建议）
  4. 复现步骤（用「类」表述，不给可复制注入串）
  5. 修复建议（按严重级优先级）
- 脱敏纪律：报告默认脱敏敏感凭据（口令 / token / 密钥 / 长 hex / base64）；不出现真实 cookie / session / 密钥。
- SRC 提交：平台模板通常要求标题 / 影响 / 复现步骤 / 危害等级 / 修复建议；证据截图与请求记录先脱敏。
- 可追溯：每个发现可回溯到测试点清单与验证记录；审计日志可查操作轨迹。

## 5. SRC 众测 / 授权真实目标实战

- **授权范围**：以平台 scope 页面 / 授权邮件为准——只测 in-scope 资产；out-of-scope 域名 / 接口 / 数据一律不碰。
- **规则与 SLA**：遵守平台测试规则（禁测项 / 限速 / 禁止批量扫描 / 禁止社工与暴力破解类）；超时与并发按平台要求。
- **数据纪律**：发现真实用户数据即停手，最小化证据（只记录必要片段），不留存、不扩散；敏感凭据一律脱敏。
- **登记与留痕**：in-scope 目标用 `--type bug-bounty` 写入 scope.json；每轮操作自动进 audit.log。
- **报告**：按平台模板提交（标题 / 影响 / 复现步骤 / 危害等级 / 修复建议）；无效 / 重复漏洞记录后排除。
- **边界**：不输出可执行 payload、不做免杀 / 钓鱼 / 社工步骤；验证到「可复现差异」即止。

## 6. 实战演练建议（靶场 / 授权目标 / SRC）

- 首次演练：DVWA（SQLi / XSS 关卡）跑通四阶段，再上 Juice Shop（API / 越权关卡）对比。
- 进阶：在 SRC / 授权平台上从低危功能（如越权 / 信息泄露类）练起，先读平台规则再动手。
- 每轮演练都写测试点清单与验证记录，养成「先过 Scope Guard、后动手」的习惯。

## 7. 留痕与报告

- audit.log 默认记录目标 / 动作 / 时间 / 结果；`audit log` 可过滤 / 导出。
- 报告草稿 → `report generate` 成稿；核对目标 / 时间 / 发现 / 证据 / 修复建议齐全、敏感信息已脱敏。
- SRC / 平台提交：按平台模板整理报告（标题 / 影响 / 复现步骤 / 危害等级 / 修复建议），证据先脱敏；不留存真实用户数据。
